# Telegram 优化后续阶段实施记录

对应 [优化方案](TELEGRAM_BOT_API_10_3_10_5_OPTIMIZATION_PLAN.md) 的 P1–P3 和 T4–T8。沿用 PTB 21.10、SQLite 和现有 Docker 镜像构建流程。

## 功能与开关

管理员通过 `/telegram_ui` 查看开关，通过 `/telegram_ui <开关名> on|off` 切换。安装后各新开关默认关闭。

Web 管理后台的首页与导航提供“Telegram 功能”入口，页面位于后台路径下的 `/telegram-ui`。六个开关与试点用户名单可在同一个表单中保存，保存后刷新机器人运行时设置。输入无效时保留表单供修正，所有字段校验通过后一次保存。Web 与管理员命令共用设置，试点用户名单留空表示全部用户。

| 开关名 | 生效范围 |
| --- | --- |
| `ephemeral_feedback` | 在频道评分成功后，向点击者显示包含本人星级、平均分和人数的临时反馈 |
| `rich_review` | 发给管理员的新审核卡片。卡片可折叠正文和审核结论，也能请求私聊全文 |
| `rich_posts` | 新投稿会话的可选发布样式，适用于纯文本和单文档投稿。媒体组、混合附件及剧透沿用普通发布方式 |
| `order_widgets` | 私聊新建的广告次数订单 |
| `slot_order_widgets` | 私聊新建的广告位租期订单，可在广告次数卡片验证后开启 |

`/telegram_ui pilot_user_ids 123,456` 限制试点用户，`all` 清除名单限制。审核卡片按收件管理员判断，频道富消息按投稿人判断。频道帖子一旦发出，频道成员按其正常频道权限查看。关闭卡片开关后，已发送订单的查单和状态刷新继续运行。

## 发送与恢复

- 评分先提交 SQLite 事务，再应答回调。临时反馈有独立时间预算，公共键盘刷新读取最新汇总并保留其他按钮。
- 富消息与普通发布共用回执。Telegram 明确拒绝富消息时使用普通文本或文档，长正文按 Telegram 长度限制分段。发送结果未知时停在原回执流程，由管理员核对。富消息来源和模板版本供纯文本视图、搜索和修复使用。
- 两类订单建立时保存网关返回的展示金额、地址和网络。金额核对仍用既有订单字段。Widget 和原生卡片按钮共用带所有者、消息和订单校验的查单入口。主动查询持久化后立即应答，JobQueue 处理网关查询。付款事务更新时，同一 SQLite 事务会排入卡片刷新。已有订单的历史展示字段保持为空。
- 迁移 002 增加富消息来源和发送格式。迁移 003 增加订单展示快照和刷新任务。容器首次启动时按顺序运行，沿用 [P0 的备份及切换步骤](TELEGRAM_P0_IMPLEMENTATION.md#数据和启动)。

## 专用 Bot 验收

使用测试频道、专用 Bot 和 UPAY 替身或测试环境。

1. 用两个账号给同一帖子评分，分别核对临时反馈的可见范围。确认公共评分最新，且原帖按钮保留。
2. 分别提交纯文本、单文档、媒体组和剧透内容。验证审核按钮、全文、频道纯文本入口、折叠文字和附件名搜索。重建索引后再搜索一次。
3. 测试新购广告次数和广告位订单，分别使用 Widget 和原生按钮查单。检查响应时限、断网、支付通知与查单并发、过期状态及重启恢复。关闭新卡片开关后再试一笔已发订单。
4. 在移动端和桌面端检查展示，并核对 Polling 与 Webhook 都收到 Widget 查询。按上述顺序单独启用各开关。
