# Telegram 优化第一阶段实施记录

日期：2026-11-23。对应 [优化方案](TELEGRAM_BOT_API_10_3_10_5_OPTIMIZATION_PLAN.md) 的 P0 / T0–T3。

## 已实现

- 沿用 PTB 21.10：验证未知字段保留及按钮参数透传；增加集中原始请求适配器、错误分类和关闭生命周期。当前不升级 Python 或 PTB。
- 分页页码和评分汇总使用统一展示按钮；管理员可选择原生禁用按钮。旧的展示回调继续应答。
- 投稿填写完成后进入确认步骤，按钮绑定随机会话编号和内容版本；修改内容后旧预览失效。确认、修改、取消均接入 ConversationHandler。
- 审核决定采用 SQLite 条件更新，只有获胜管理员建立发布操作；其他管理员卡片按已提交结果刷新。
- “拒绝并拉黑”增加确认，等待真实异步拉黑结果；失败时显示“已拒绝，拉黑未完成”。
- 普通投稿与人工审核发布共用逐步发送记录：请求前记录发送中，响应后保存全部消息 ID；超时不自动重试，不继续发送后续组。
- 媒体和文档按 Telegram 支持的组合发送，文档超过 10 个时分组；保留长说明、回复关系和剧透设置。
- 已知部分成功保留回执；结果未知时不退款。启动恢复将中断发送标为待核对，确定未发送的已扣次操作可幂等退款。
- 购买入账、消费、退款各自绑定唯一流水键；只有首次购买流水写入才加余额。旧流水不重算。
- 购买次数订单与广告位订单的主动查单都先校验用户归属；图片订单反馈编辑 caption。
- 管理员能核对发送结果、明确重试和修复帖子记录/搜索索引；修复索引不重新发帖。
- Polling 与 Webhook 共享更新类型列表；启动不会调用 setMySettings 改变隐私、入群或话题设置。

## 管理员入口

所有入口沿用 `ADMIN_IDS`（含已有 OWNER）校验。

| 命令 | 用途 |
| --- | --- |
| `/telegram_ui` | 查看原生禁用按钮开关 |
| `/telegram_ui disabled_buttons on` | 为后续渲染开启原生禁用按钮 |
| `/telegram_ui disabled_buttons off` | 使用兼容展示按钮 |
| `/publish_status 123` | 查询操作状态、已知消息 ID 和异常类别 |
| `/publish_resolve 123 sent 456,457` | 人工核对频道后，确认该操作已完整发送；保留所有已有回执 |
| `/publish_resolve 123 not_sent confirm` | 核对后确认完全未发送；禁止对已有成功回执的操作这样处理 |
| `/publish_retry 123 confirm` | 明确重试确定失败或已知缺失步骤，使用原内容快照 |
| `/publish_repair 123` | 从已确认的回执与快照重建记录/索引，不发频道消息 |

`unknown` 必须先核对，不能直接重试。`partial` 只有在不存在未知步骤时才允许补发。

每次明确重试生成关联子操作；相同父操作只创建一次子操作。成功步骤复制回执并复用，缺失步骤才发送。确定失败并已退款的操作重试时绑定新的扣退编号；部分发送的重试沿用原消费关联，防止再次收费。父操作的查询结果保留子操作编号。

“确认已发送”是管理员对实际频道消息的人工核对，不代表 Bot API 可以自动查询任意历史消息。消息 ID 必须来自本次操作对应的频道内容。

## 数据和启动

新增编号迁移、稿件会话/版本、操作表、发送步骤、消息视图，以及可空唯一账本键。迁移运行在初始化事务中，可重复执行，错误直接阻止启动。

历史稿件获得会话编号；旧格式确认按钮需要重新预览。历史账本的 `idempotency_key` 保留 NULL，不猜测消费归属，不重新计算用户余额。

沿用单运行实例部署。发布时先备份 SQLite 数据及关联文件，并停止旧实例，再启动包含本次代码的实例；不要让旧、新程序同时使用同一数据库进行启动恢复。首次启动会迁移，随后按已有部署方式检查健康状态。

回退优先关闭新 UI。新操作和账本已写入后，应使用保留本次事务逻辑的兼容构建，不直接换回不理解这些记录的旧版本。

## 验证范围

在隔离代码副本与临时 SQLite 数据库中验证；外部 Telegram/UPAY 传输使用替身，没有调用生产 Bot、创建真实订单或读取生产数据库。

覆盖重复入账、并发确认、审核竞争、旧预览隔离、唯一扣退、未知发送、部分发送补发、启动恢复、人工核对、旧库迁移、查单归属和图片说明编辑。

另有实际 PTB Application / ConversationHandler 的模拟端到端流程，验证确认后会话结束、仅发送一次、再次点击旧预览不重发。

原生能力的真实服务端验证需使用专用 Bot；开关初始关闭。本轮不启用 P1 个人临时反馈、P2 富消息或 P3 Widgets。

最终完整回归：334 项通过、1 项跳过；新增 31 项验证。操作记录模块行覆盖率 92.94%，逐步发送模块行覆盖率 91.67%。源码与测试同步到项目后，运行实例仍需按现有部署流程发布。
